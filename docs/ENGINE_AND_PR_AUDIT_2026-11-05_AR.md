# تدقيق المحرك والسكريبتات وطلبات السحب — 2026-11-05

## الخلاصة التنفيذية

اترفعت إصلاحات المحرك والاختبارات وبوابات التدقيق ونسختا Windows المحدّثتان إلى `main` في commit **`b7480cdbcffc6b13ed63e99ecb8fecaa6cd4939f`**. رأس `origin/main` اتأكد بعد الدفع إنه نفس الـcommit، وشجرة العمل كانت نظيفة.

لم أدمج أيًّا من طلبات السحب المفتوحة العشرة في هذه الجولة: فحص `git merge-tree` مقابل `origin/main` بعد التحديث وجد تعارضات دمج حقيقية في كل واحد، وكمان ظهرت عيوب أو بوابات اختبار أضعف في بعض الفروع. ترك الطلبات مفتوحة بدل دمج تغييرات ممكن ترجع سلوكًا أقدم أو تمرّر فشلًا على إنه نجاح.

## الإصلاحات التي اتنفذت واترفعت

- **GML VM:** إصلاح `"text" + number`؛ التنفيذ كان بيحوّل الطرف الرقمي إلى سلسلة فارغة، فكان الناتج يسقط الرقم. دلوقتي يتحول الطرف الرقمي إلى نص بتنسيق `%g`. أضفت اختبارين regression للتعبير العادي ولـ`+=`، وضمّنت الاختبار في مجموعة المحرك. اتزامن `gml_vm.c` والاختبار مع `cpp_backup` وحزمة المصدر.
- **Parity المرايا:** فحص `verify_core_mirrors.py` بقى يقارن كمان ملفات C/H الموجودة في جذر كل شجرة، ويتأكد من تطابق اختبار `test_gml_vm_execution.c` نفسه في المرايا؛ الفحص كشف اختلاف نسخة `gml_vm.c` وتمت مزامنتها.
- **Host pipeline:** بقى يشترط وجود عينات Mario وPlataformas وShooter وZelda الأربع بالاسم، ويتحقق من exit code وعلامة النجاح الدقيقة لكل تشغيل؛ غياب عينة أو فشل اللعبة يخلي السكريبت يرجع فشل حقيقي.
- **Audit runner:** بقى يفشل لو أي builtin مستهدف غير موجود بدل ما يعرض النقص ثم ينهي التدقيق بنجاح. فحص وجود الاسم في المصدر لا يثبت وحده أن الدالة موصولة وقت التشغيل؛ لذلك لا أعتبره بديلًا لاختبارات dispatch.
- **Baseline report:** أُعيدت كتابة المولّد ليعتمد على نتائج الأوامر الفعلية، والتاريخ ومدة التشغيل وعدد اختبارات Python، ويكتب `PASS/FAIL` ورمز خروج مطابقين للنتيجة. بقى يوضّح كمان إذا كان working tree متغيّرًا، وما بيدّعيش بناء Android أو اختبار جهاز فعلي.
- **Windows:** أُعيد بناء `NorMakerStudio.exe` و`NorMakerNativePC.exe` وتحديثهما في `desktop/windows/dist`، واتحدثت أحجامهما وبصماتهما في README.
